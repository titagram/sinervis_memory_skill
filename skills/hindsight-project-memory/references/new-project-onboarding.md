# New-project onboarding

Use this exact, project-neutral chat sequence for every unknown workspace. It keeps registration, remote bank creation, connector mapping, and source ingestion as separate actions.

1. **Discover boundaries.** Read the applicable instructions, identify repository roots and nested repositories, and state what paths are in scope. Do not infer a product from a directory name.
2. **Identify the operator.** Show the active operator. Ask for a nickname only when no active operator exists; persist it only after the user replies.
3. **Confirm product boundary and owner.** Ask whether the workspace is a new independent product, a repository within a named existing product, or uncertain. Ask for the owner namespace and display name when they are not already explicit.
4. **Propose, do not register.** Run `project propose` with an explicit root, owner, and name. For new normalized owner/project slugs, name the fields exactly: `bank_id = <owner>::<project>` and `product_identity = <owner>-<project>`. Present those fields, the relationship, and a per-project source policy: authoritative source locations, excluded data/build outputs, logbook/event handling, graph capability and its audit prerequisite, initial dossier topics, and `credential_policy`. New/unconfigured projects default to `exclude`; use `allow_project_staging` only when the user explicitly approves credential-bearing selected sources for that private project.
5. **Confirmation gate: relationship and profile.** Ask the user to confirm the root, product boundary, bank ID, source policy and credential policy. Mark the resulting JSON profile `reviewed: true` only after that answer. A proposal has no persistence effect.
6. **Confirmation gate: local registration.** State active operator, root, bank, and the local registration action. Only after explicit confirmation use `project register --confirm`. The local audit intent must succeed before registry mutation; preserve the completion result or report audit uncertainty.
7. **Confirmation gate: bank creation.** Creating a Hindsight bank is a separate remote write. State the same summary and wait for an explicit remote-write confirmation; never treat local registration as bank creation.
8. **Configure project-neutral missions.** After the bank exists, configure retain/observations/reflect missions for the confirmed project policy, with provenance, source precedence, secret handling, and fail-closed uncertain claims. Do not copy another product's prompts, sources, or observations.
9. **Run a dry inventory.** Produce a local candidate inventory and preflight/redaction result first. No retention occurs in this step. Present document count, blocked candidates, and graph-audit status before any ingestion confirmation.

## Second repository of an existing product

When a workspace might be a second repository, ask: “Is this repository part of product `<product identity>` and should it share bank `<bank id>`?” Reuse is allowed only after the user confirms that relationship and a reviewed profile supplies the same explicit product identity as the registered roots. The proposal preserves the existing bank identity but remains confirmation-required. Registration does not alter the old repository's attribution or history; connector remapping remains a later, explicit operation.

If candidates with that product identity point to more than one bank, or the relationship cannot be established from user-provided facts, return an uncertainty result with exit code 2. Do not register, create a bank, update a connector, create a backup, or ingest anything until the user resolves it. Connector synchronization additionally requires an active operator, exact reviewed root/bank/product/relationship binding, a successful write-ahead audit, and `connector sync --confirm`.

## Isolation and source policy

Every project begins with its own policy rather than inheriting another product's values. The policy must name source-of-truth material, approved temporal logs, optional audited graph inputs, initial dossiers, exclusion patterns, credential policy, and the verification command for each derived source. Safe future metadata is permitted, including token budgets/counts, password policies, secret handling, credential rules, absolute project roots, and ordinary safety prose; actual credential values remain forbidden in profiles, registry, audit, summaries, diagnostics and tags.

`exclude` redacts or blocks credential-bearing source content. `allow_project_staging` requires `reviewed: true` and allows credentials only when a regular in-root text source's canonical relative POSIX path is listed exactly in `source_policy.credential_sources`; unselected candidates retain the default `exclude` behavior. It does not authorize crawling, symlinks, out-of-root files, binary data, dumps, uploads, customer/payroll/medical data, generated outputs, caches or dependency trees. This is deliberately semantic rather than a generic entropy or substring ban, so harmless future project metadata stays supported. A reviewed product may opt into `allow_project_staging`; another project does not inherit that choice. A graph is only a derived navigation aid after its project-specific audit passes; it never becomes source authority.
