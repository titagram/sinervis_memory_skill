# Reading protocol

Use this order:

1. Resolve the canonical registered project root and its bank. Stop for onboarding when the boundary is unknown; never borrow a similarly named project's memory.
2. Search the project's Knowledge Pages first for cold-start orientation.
3. Recall granular evidence: facts, source/event IDs, paths, hashes and timestamps.
4. Reflect only for cross-source WHY, rationale, decision, supersession or impact questions.
5. Inspect every material result's layer, trust, event time and provenance. Source/event/graph/dossier labels describe different authority, not interchangeable evidence.
   For document inventory and duplicate/stable-ID checks, page through the official document `items`, preserving IDs, metadata, `total`, `limit`, and `offset` while excluding document content and server diagnostics.
6. When freshness is material, compare retained source/graph hashes and generator metadata with the live source.
7. For diagnosis or modification, verify through current wiki MCP, code, YAML, templates, router, tests or mobile consumers required by the workspace. Memory is the navigation map, not a replacement for live evidence.
8. Answer with cited paths/IDs, current-versus-historical state and explicit uncertainty.
9. If verification disproves memory, propose a correction only after the live check. Writing follows the separate mutation recipe and confirmation gate.

Knowledge Pages use the project's controlled `knowledge:*` vocabulary. An empty page is a query/tag/configuration symptom to inspect, not evidence that the bank contains no relevant facts.

Credential-bearing retained sources follow the same evidence rules. Use their values only when the project policy permits them and the task requires them; never reproduce them in audit, command summaries or transport diagnostics.

Reading is non-mutating. Do not treat an inspection request as authorization to retain corrections or refresh derived material.
