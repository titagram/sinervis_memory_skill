# Project registration

Registration is a local, explicit decision. It never creates a Hindsight bank, changes a connector mapping, or ingests project files by itself.

## Required inputs and gates

Use explicit temporary or project-scoped paths while reviewing the workflow; do not rely on a home-directory default. The operator is shown before any registration write and must already be active.

1. Generate a proposal with a canonical root, owner namespace, display name, ASCII `project_slug`, proposed `bank_id`, product identity, and relationship.
2. Review the JSON profile outside the proposal command. Set `reviewed: true` only after the user has confirmed its root, product boundary, bank, source policy and project-level `credential_policy`.
3. State the active operator, root, bank, and action, then pass `--confirm` to `project register`. The CLI writes a non-secret audit intent before changing the registry and a completion record afterwards. A proposal alone never persists.
4. Create the remote bank only in the separately confirmed remote operation.
5. Synchronize the connector only with `connector sync --confirm`, explicit connector/registry/profile/audit paths, and the reviewed resolved profile. It writes an audit intent before making a backup or changing the connector. Remapping is separate from registration and needs its own confirmation in chat.

`project register` reads a profile from `--profile FILE` or standard input. The project-level `credential_policy` accepts exactly `exclude` and `allow_project_staging`; an absent value resolves to `exclude`. `allow_project_staging` requires `reviewed: true` and a nonempty `source_policy.credential_sources` list of exact canonical relative POSIX paths. The registry stores the policy and selectors, never credential values. Credentials are permitted only in the later retained content of a selected in-root source, not inside the profile itself.

Before a first export, enrich a minimal registration with the project-specific policies that the selected commands consume: source inclusion/exclusion and credential selectors, source/event scope and knowledge-layer rules, optional `graph_policy`, explicit non-empty Knowledge Page specs, and benchmark policy. This is a separate local registration update: generate the proposed JSON, display a content-free diff, obtain confirmation, set `reviewed: true`, then run `project register --confirm --profile ...` with explicit registry and audit paths. Do not let export commands invent missing fields or silently no-op. The schema remains project-neutral; product-specific paths, topics, graph coverage and page queries belong only to that product's reviewed profile.

The active operator remains registry state. A stored project profile need not duplicate it. Manifest and graph build commands resolve the active registry operator at execution time and inject that exact value into `user:<operator>` plus metadata; an absent or placeholder operator fails before an eligible artifact is built.

Registration requires known canonical identity fields, permits safe JSON-compatible project metadata for future policies, and recursively rejects actual credential-shaped keys or values at both the CLI and registry boundaries. Detection recognizes semantic adjacent key pairs in camel/separator forms and a small set of concrete credential formats (including PEM private keys, JWTs, GitHub, OpenAI, Slack, and AWS access-key IDs); it does not use generic entropy heuristics. Policy/measurement fields such as `token_budget`, `token_limit`, `token_count`, `password_policy`, `secret_handling`, and `credential_rules` remain valid metadata, as do canonical absolute path mapping keys. It rejects an unknown credential policy, an unreviewed profile, a missing operator, and an uncertain relationship. Successful output is an operational summary rather than the supplied/stored profile. Its local audit entry identifies the operator, root, bank, action, timestamp, phase, result, and run identity; it never contains content or credential values. If the intent audit cannot be written, the target is not changed; if a completion audit fails, the outcome is reported as audit-uncertain while the intent remains attributable.

## Product boundaries and bank reuse

The normal proposal for a new project remains one production bank per product knowledge boundary: `<owner>::<project>`, with product identity `<owner>-<project>`. Owner and project are normalized to lowercase ASCII slugs with hyphens; an empty normalized slug is rejected. In a reviewed explicit profile, `project_slug` is the stable retained-document and project-tag identity and need not equal the bank's project component. `bank_id` remains a canonical two-part lowercase slug ID and its owner component must equal `owner_slug`; for example, Acme Portal uses project slug `acme-portal` with bank `acme::portal`.

An additional repository can reuse a bank only when the reviewed profile explicitly says `relationship: existing_product_additional_root` and has the same reviewed `product_identity` and `project_slug` as every existing root for that bank. This keeps stable document IDs and `project:*` tags in one namespace across the shared bank. For example, a mobile repository explicitly confirmed as part of `acme-portal` can resolve to `acme::portal`; an unrelated repository called "Acme Portal tools" cannot inherit it. Ambiguous or absent product identity fails closed with a confirmation-required result and no local mutation.

Refreshing the same canonical root and bank may enrich metadata, but cannot change an already established owner slug, project slug, product identity, or relationship. Such a change requires an explicit remap workflow. Refreshes preserve the original `registered_by` and `registered_at`; they record the current operator in `updated_by` and `updated_at` instead.

## Connector synchronization

`connector sync --confirm` requires an active operator before it can audit, back up, or write. It first loads the full connector JSON and requires `mapPathToBank` to be a JSON object. The reviewed supplied profile must match the registration's canonical resolved root, bank, owner slug, project slug, product identity, and relationship. It validates the serialized round trip and permits only the exact resolved `mapPathToBank` entry to differ. Before replacement it writes an audit intent and makes a private `coding-agent.json.project-memory-backup-<UTC timestamp>` backup. The output reports only root, bank, and backup path—never connector settings, profiles, or tokens. Malformed JSON, a non-object mapping, an unregistered root, missing operator/confirmation, audit failure, or a profile mismatch leaves the configuration and backups untouched.
